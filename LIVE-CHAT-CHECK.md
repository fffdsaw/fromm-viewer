# Read-only LIVE chat check

The user's browser is playing a LIVE but is not connected to this chat's browser tools. This feature lets the user run the official read paths in the already authenticated Viewer and copy only a sanitized result. It does not establish that the current account has successfully received comments until the user runs it.

In an ordinary LIVE, click **댓글 확인**. The transient status overlays the bottom of the normal video. **진단 복사** copies presence flags, fixed result codes, permission booleans, message/deletion counts, cursor-presence flags and known field types. No account/room IDs, URLs, token values, cursor values, nicknames or comment contents are copied. The status can be dismissed and is not included in video-only PiP.

The check uses only `liveChat.chatToken` from the current normal `/enter`, requires `chatProvider=fromm` and `entry.kind=channel`, and never falls back to the account token, Agora token or artist token. It issues `GET /live-chat/rooms/{roomId}` and two cursor-based `GET /live-chat/{roomId}/messages` samples two seconds apart to the fixed HTTPS `live-chat-api.frommyarti.com` origin. These paths, the separate bearer token, initial millisecond cursor and envelopes are supported by the retained official Android 1.50.2 source/bytecode evidence in LIVE-UI-NOTES.md. The room ID is the current ordinary LIVE room ID; the official chat room state model itself has no ID field.

There is no send, like, moderation, rejoin, token-renew or background polling action. No request starts until the user clicks. A ban stops the probe before message requests. An empty authorized response is reported separately from actual message receipt. Unknown response formats, authorization errors, network failures and timeouts never report receipt.

Room/account/playback changes and closing the diagnostic abort pending work. The Native helper, existing frame/ACK/audio path, PiP module, extension rules, origin allowlists and media download behavior remain unchanged. The chat request uses the Viewer's captured native browser fetch rather than sending the separate chat bearer through its localhost account proxy. Cross-origin browser support is still a runtime test; the existing extension's broad read CORS response rule may apply, but no new bypass or API-host permission is added.

Local/CI fixtures use only synthetic tokens and intercepted service responses. Those fixtures cover privacy, schema errors, 401/403/429, no automatic requests, no writes, cancellation, narrow layout and PiP preservation. Actual Fromm account access, live messages and posting are **UNCONFIRMED** until real browser results are supplied. Sending a test comment remains outside this read-only check and requires the user to specify the actual text.
