# LIVE comment overlay and read-only checks

The user's authenticated browser is not connected to this chat's browser tools. On 2026-10-16 the user ran the deployed normal-account probe: room state and two message-list GETs succeeded, with provider `fromm`, frozen=false, banned=false and mutePresent=false. The first run was empty; a subsequent run received three message objects in its second sample. This establishes actual authenticated read transport and nonempty comment receipt. Posting remains unverified.

In an ordinary LIVE, click **댓글 보기**. Actual nickname/content pairs appear over the bottom of the normal video on a translucent gradient. The input explicitly states that only reading is supported and stays disabled. **댓글 숨기기** or **닫기** stops reading. PiP continues to contain only video.

**진단 복사** copies presence flags, fixed statuses, permission booleans, message/deletion counts, cursor-presence flags and known field types. No account/room IDs, URLs, token/cursor values, nicknames or comment contents are copied. Comment content remains in the normal page's bounded memory/DOM; it is never persisted to storage, files or diagnostics.

Reading uses only `liveChat.chatToken` from the current normal `/enter`, requires `chatProvider=fromm` and `entry.kind=channel`, and never substitutes account, Agora or artist tokens. It requests the official room state and cursor-based messages from fixed HTTPS `live-chat-api.frommyarti.com`. The client starts at the current millisecond cursor, advances only to a returned cursor and waits two seconds between completed requests. Room policy is refreshed every 15 samples. Each request has an eight-second timeout. Paths, auth, initial cursor and envelopes follow the retained official Android 1.50.2 source/bytecode evidence and now have the normal-account runtime check above.

There is no send, like, moderation, rejoin or token-renew action. No request starts before the user clicks. A ban stops reading and removes comments; authorization failures also clear them. Empty responses, actual receipt, unsupported message fields, network failures and timeouts are distinct. Reading stops with a visible error instead of silently claiming success or repeatedly retrying denied requests.

The official `LiveChatMessageModel` provides `messageId`, `content`, `nickname`, `createdAt`, `userId` and `role`. Only validated ID/content/nickname/time fields are used, and `userId` is not retained. Rendering uses textContent, never HTML. IDs deduplicate messages, deletion tombstones prevent immediate resurrection, and repeated evicted messages are ignored. Memory is capped at 100 comments, 2,000 recent IDs, 500 deletion IDs and eight sanitized diagnostic samples; only the latest 30 rows are rendered. Desktop/mobile overlays remain inside the stage and do not add a panel below it.

Room/account/playback changes and closing comments abort pending work. The Native helper, frame/ACK/audio path, PiP module, extension rules, origin allowlists and downloads are unchanged. Requests use captured native browser fetch, keeping the chat bearer out of the localhost account proxy. No new CORS rule or host permission is added; the user supplied successful browser read results with their existing setup.

Synthetic fixtures cover privacy, schema errors, 401/403/429, opt-in GET-only behavior, cursors, duplicates, deletions, bounded memory, ban refresh, cancellation, XSS text rendering, narrow layout and actual image-only Document PiP while comments remain on the main page. Actual authenticated read/three-message receipt is supported by the user-supplied probe result. The new overlay's real-account presentation and posting are still **UNCONFIRMED** until the user reloads and views it. No real test comment has been sent.
